

## RC-057 — the device leg reaches a Linux host through a loopback front 2026-10-08 (UTC)
- **Route that failed:** pointing the emulator at `https://10.0.2.2:<port>` with the host's certificate installed as a system CA (the emulator needs `-writable-system` plus a remount for that, both done). The device could reach the port (`nc` succeeded) and the CA file was in `/system/etc/security/cacerts`, but the app still reported `Host readiness unavailable` and the host's log showed no request, so the trust route was abandoned rather than guessed at further.
- **Route taken:** the device talks plain HTTP to its own loopback (`adb reverse`), and a small Bun front on this Mac (`scripts/rc057/http-front.ts`) is the loopback peer the API accepts and speaks TLS to the host. It relays the event WebSocket with the app's own cookie, and drops the `Secure` attribute on that one hop because a phone never sends a Secure cookie over plain HTTP — the front is the device's loopback and the next hop is TLS.
- **What that unlocked:** the app now signs in to the Linux host, lists the workspace the host holds, takes the screen over (`Possession: holder`) and has had a text input applied by the host (`The host applied the text.`).
- **Still open:** after an input the session panel's controls are disabled, which the proof shows comes from its parent passing `blocked` — `apps/mobile/src/features/workspaces/WorkspacePanel.tsx` sets `busy` in `mutate`/`loadReceipt` and clears it only when `duringMutation` is false, so a stuck `busy` there disables the child's input row for good. The session panel's own gate was already fixed to release per operation; the parent's needs the same treatment before the click, return, drop-and-recover legs can run.
