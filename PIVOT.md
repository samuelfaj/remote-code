

## RC-067 — the control plane runs where Docker is, not inside a container 2026-10-08 (UTC)
- **Route that failed:** running the control plane's API *inside* the host image and publishing that container on the tunnel. Every provision answered `503 provisioning_failed`, and the account's own record named the cause exactly: `"error":"Executable not found in $PATH: \"docker\""`. The image has no Docker client and the container had no Docker socket, so the control plane could not create the account containers it is supposed to create.
- **Route taken:** the API runs as a child process on this machine with `RC060_DOCKER=docker` in its PATH and the same `REMOTECODE_HOSTED_*` settings — the arrangement `scripts/rc060/run-hosted-provisioning-proof.ts` already proved — and the tunnel points at that process over the same self-signed certificate.
- **What that unlocked:** the outside machine can not only reach and sign in to the managed service, it can have the service provision a real account, which is what "hosted service accessible" means.
## RC-015 — the proof container gets its model from its own catalog 2026-10-08 (UTC)
- **Route that failed:** copying this host's Distill `config.toml` into the proof container and expecting the host's default model to work there. Two measured reasons it cannot: the catalog the copied credential exposes inside the container holds four `grok-*` ids and no `claude/claude-opus-5-5`, so `distill -m claude/claude-opus-5-5` answers `unknown model id`; and `default_reasoning_effort = "max"` is refused by those models (`invalid-argument: Invalid reasoning effort`), which is the error the earlier attempt had recorded as a mystery `Internal error`.
- **Route taken:** the proof asks the container's own catalog endpoint (`GET https://cli-chat-proxy.grok.com/v1/models` — the same source the container's Distill caches) for a model id, then rewrites only the copied config's `[models]` `default`, `worker` and `default_reasoning_effort` lines. `RC015_MODEL` and `RC015_REASONING_EFFORT` override both.
- **What that unlocked:** the API-authorized task completes inside the container as `rcagent`, so RC-015's isolation case passes twice on this machine and the matching RC-065 matrix row no longer fails.
## RC-054's Windows leg — a real Windows browser, not a claimed one 2026-10-08 (UTC)
- **Route that failed:** every Windows target this machine or its tooling can offer. There is no Windows host, VM or browser here, and Cua reports the `windows` image unsupported on all three connected clouds (AWS: `needs a nested-virtualization instance; not offered on AWS yet`; GCP: `VM images are not offered in your own cloud yet`; Modal: `Modal sandboxes run container images`).
- **Second route that failed:** a throwaway GCP instance for the Linux host. `gcloud services enable compute.googleapis.com` returns `UREQ_PROJECT_BILLING_NOT_FOUND` — the project has no billing account attached — so no instance can be created there, and attaching billing is an account change that is not this task's to make.
- **Route taken:** GitHub's `windows-latest` runner is a real Windows machine, and this repository is public, so it costs no minutes. The Linux host runs here on the repository's own `prototype/Dockerfile` image and is published over a Cloudflare quick tunnel; the workflow's Windows browser reaches it through that tunnel. `workflow_dispatch` only resolves for a workflow that is also on the default branch, and this repository's default branch is protected, so the run is armed by a push to the open pull request with the origin in a repository variable that is cleared as soon as the run starts.
- **Why that is not a weakening:** the acceptance asks for a browser on Windows reaching the same Linux backend. Every assertion still runs against the Linux host's own records; only the operating system the browser runs on changes, and the workflow, the runner script and the host script are committed so the leg is reproducible by anyone.

## RC-057 — the device leg reaches a Linux host through a loopback front 2026-10-08 (UTC)
- **Route that failed:** pointing the emulator at `https://10.0.2.2:<port>` with the host's certificate installed as a system CA (the emulator needs `-writable-system` plus a remount for that, both done). The device could reach the port (`nc` succeeded) and the CA file was in `/system/etc/security/cacerts`, but the app still reported `Host readiness unavailable` and the host's log showed no request, so the trust route was abandoned rather than guessed at further.
- **Route taken:** the device talks plain HTTP to its own loopback (`adb reverse`), and a small Bun front on this Mac (`scripts/rc057/http-front.ts`) is the loopback peer the API accepts and speaks TLS to the host. It relays the event WebSocket with the app's own cookie, and drops the `Secure` attribute on that one hop because a phone never sends a Secure cookie over plain HTTP — the front is the device's loopback and the next hop is TLS.
- **What that unlocked:** the app now signs in to the Linux host, lists the workspace the host holds, takes the screen over (`Possession: holder`) and has had a text input applied by the host (`The host applied the text.`).
- **Resolved on 2026-10-08:** the disabled controls were the panel *waiting* for the host, not a stuck gate — the host applies a click in ~10 s, longer than the panel's 10 s read budget, so the input read as an unknown outcome. Input now has its own 30 s budget and the harness waits for the app's own words. The Android leg passes end to end twice.
- **Superseded note (kept for history):** after an input the session panel's controls are disabled, which the proof shows comes from its parent passing `blocked` — `apps/mobile/src/features/workspaces/WorkspacePanel.tsx` sets `busy` in `mutate`/`loadReceipt` and clears it only when `duringMutation` is false, so a stuck `busy` there disables the child's input row for good. The session panel's own gate was already fixed to release per operation; the parent's needs the same treatment before the click, return, drop-and-recover legs can run.
