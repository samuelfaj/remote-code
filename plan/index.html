One host per user, visual sessions per Bot

RemoteCode remains inside a single Linux container per user. Each Bot can have its own screen and browser session within it, linked to the thread, without creating another container per Bot. Host files and credentials may be accessible by other Bots of the same user; separate screens are not security isolation. The profile and credential policy needs to be clarified before beta.

Under human control, the viewing and input session must be authenticated, temporary, and revocable. The backend must block Bot computer tools during intervention, stop capture intended for the agent while the user types sensitive data, and expire control with explicit recovery after disconnection. The Bot only resumes action after receiving the session back and observing the page again.

02 / How it works

The Mac stops being the host. The container becomes the host.

The current macOS app is the function reference. In the new product, execution and data move to the user's Linux container. Clients use the backend's typed API; the visual session is opened on demand to monitor or take over the Bot's computer.

Clients

React Native + common core

Browsers, Linux GUI, iOS, and Android use the same services and HTTP/WebSocket connection. Screens follow the device.

→

Account and gateway

They identify the user and route API and events only to their container.

Host

TypeScript + Elysia

Backend in the Linux container per user: workspaces, Bots, Distill, files, terminal, GUI, and tasks. Volume and backup preserve the work.

Web + macOS + Linux + Windows

A desktop UI

React Native Web renders the interface in clients' browsers and in the Linux GUI window inside the container. Terminal, Git, Distill, and automation run only on the Linux host. Clients send actions via HTTP and receive events, terminal, and remote screen via WebSocket; shortcuts are handled in the interface and sent to the host when they are remote commands.

iOS + Android

Mobile UX on the same core

React Native with screens designed for touch, notifications, and returning to the conversation. It consumes the same services, state, and components that work well on the device; navigation, layout, and device integrations are native.

One client core for all platforms

A shared package centralizes the Eden client, connection authentication, workspace services, Bots, threads, and tasks, error handling, cache/state, and event reconnection. Web, Linux GUI, and mobile import this package; they do not maintain parallel implementations of API calls. Each platform provides only the adapters needed to store the session, open notifications, and control the remote screen.

Remote app

React Native Web calls Elysia/Eden via HTTP and receives events via WebSocket. Workspace, files, terminal, Git, threads, and Bots belong to the container; no command runs on the client device.

Bot's eyes and hands

linux-use runs on Linux as Distill's local MCP server. It must identify the correct window/session, observe the GUI, and send actions with state validation. Currently, only X11 window diagnostics and listing exist; capture, click, and typing still need to be implemented and proven.

Screen for the person

A local service streams the Bot's graphical session to the authorized client and receives mouse and keyboard via an authenticated remote channel. The backend grants exclusive ownership: during human login, linux-use cannot act on that session. Connection drop revokes old input and requires reconciliation before returning control to the Bot.

Single contract between backend and clients

The TypeScript backend exposes Elysia routes and exports the application type. The shared core uses Eden Treaty for typed calls of workspaces, Bots, threads, and tasks. Types assist development; the backend continues validating data and authorization at runtime. Long-lived events and the remote screen maintain their own channels linked to the same identity and resources.

Isolate the backend from agent actions

The backend and Distill remain in the user's container but run with distinct identities and permissions. Commands executed by the agent do not receive gateway tokens, direct database access, or backend secrets; these operations go through authorized APIs. The container is not the isolation boundary between Bots. In the hosted offering, each user starts in their own VM.

Version compatibility

Eden types client and server in code; installed apps and self-hosted servers can run different versions. The API exposes version and capabilities, validates inputs on the server, and declares which client versions are accepted. An incompatible client shows the reason and required action without corrupting data.

One action, one authority

If you send a message on the web, the backend of the container accepts and executes it. In computer control, the backend grants screen control to the user and prevents simultaneous Bot actions; after return, it confirms the state before resuming.

The container is not the backup

Image and process can be replaced. Workspaces, Bot memory, threads, attachments, tasks, preferences, browser sessions, and receipts need to survive in volume and tested backups.

When you close the page

  • Agents, Bots, and tasks continue running on the Linux host.
  • The web reconnects with a snapshot and then applies new events.
  • Push notifies you when there is a result, failure, or approval.
  • If the container restarts, the app shows what was recovered and what was interrupted.

Install or subscribe

  • Self-managed: open source, RemoteCode image and volume under user control; basic use independent of our hosting account.
  • Hosted: the same image, with provisioning, updating, monitoring, backup, and support operated by us.
  • In the hosted pilot, one VM per user protects isolation while we measure cost and capacity. The container is the software unit.
03 / When something breaks

Fail in a recoverable way and without lying about the result.

No plan can list all future errors. Each product boundary will have a response deadline, persisted state, recovery responsible, and a safe behavior for unknown failures. The general rule: do not lose confirmed work, do not repeat uncertain external effects, and never present “completed” without backend confirmation.

1 · Before accepting

Failure without effect

If authentication, validation, or capacity fail before the backend accepts the operation, return a clear error. Reads may retry with limits and increasing wait; writes use a stable operation ID.

2 · Uncertain result

Check the receipt

Timeout or crash after sending does not prove the write failed. Check the durable state by ID before resending. If there is an external effect without a reliable receipt, mark “unknown result” and request verification, without automatic retry.

3 · After confirming

Reconcile the screens

If the response or event is lost after commit, snapshot and cursor recover the state. The same ID returns the same result, and web/mobile remove provisional states when the server diverges.

Docker or process stuck

Healthcheck measures real progress of the API, Distill, and GUI. A supervisor on the host, outside the container, observes failures with a maximum deadline, avoids restart cycles, and offers step recovery: reconnect, restart process, recreate container with the same volume. If Docker does not respond, show “unavailable” and alert; do not declare recovery or erase volume.

Slow network and requests

Each operation has a total deadline and visible cancellation. Reads allow limited attempts with wait and jitter; message sending, editing, Git, scheduling, and billing require an idempotency key or receipt query. App crash does not cancel an already accepted job.

Distill and commands stuck

Run has heartbeat, deadline per step, and stop command. Process without progress receives diagnosis and controlled shutdown; after restart, state remains interrupted or unknown until reconciliation. Tool with uncertain external effect is not automatically rerun.

Providers and expired accounts

Invalid or expired credential requests new authentication. Usage limit and temporary unavailability show reason and next allowed attempt; wait and retry only happen when the operation is safe. Changing model or account never hides a failure nor changes user choice without authorization.

Disk, database, and memory

Full disk, unavailable database, corruption, and memory pressure block new mutations before losing receipts. The app shows capacity and degraded state, preserves backups, and only returns to writing after integrity proof. Limits and queues prevent one Bot from taking down all others of the user.

Events, push, and remote control

Events have cursor and deduplication; gap forces new snapshot. Push is an alert derived from the durable Inbox. Takeover uses exclusive possession with deadline and generation: disconnection or restart revoke old control, prevent delayed clicks, and require explicit resumption.

Routines, versions, and payment

Schedules have a key per occurrence and do not repeat uncertain effects; timezone and time change follow explicit policy. Update preserves volume and allows backup restore. Duplicate or out-of-order payment webhooks reconcile with the provider before changing access. Incompatible client with the API stops before writing.

How to know that recovery works

The backlog requires injecting failures before, during, and after commit; disabling network; freezing Docker, Distill, and GUI; filling disk; restarting during routine and takeover; duplicating events and webhooks; restoring backup and testing client of different version. Each scenario must end in confirmed success, harmless error, or unknown result that requires human reconciliation. None of them can become presumed success.

04 / What must exist

RemoteCode functions, with Linux host.

Preserve relevant journeys from the current app with Linux host and Distill as the only harness. Each block below must work in the container and be accessible through the appropriate interfaces.

Distill is the only agent engine

Worker threads and Bots start sessions of Distill in the Linux container. Models and accounts are configured by it; RemoteCode presents conversations, permissions, progress, and results in its own interface.

The biggest technical work

The current GUI uses AppKit/SwiftUI and macOS services. Migrating these journeys to React Native and moving authority to Elysia on Linux requires proving terminal, files, Bots, remote desktop, and Distill on each client; shared types do not replace this proof.

In the current macOS app, BotDesktopKind.dockerDesktop already offers a Docker screen for the Bot, but the code itself states that agent, files, and workspace remain on the Mac. The new product needs to also move these components to the user's Linux host and replace the current Bot container organization with the organization defined here.

05 / Journeys

How to know the product is right.

01

Continue from another device

Open a project in the desktop GUI, edit via web, follow along on iPhone or Android. File, thread, and result are the same. Changing selection on the phone does not steal focus from the desktop.

02

Leave an agent working

Start a run, close the browser, come back later. The run maintains the real state; if approval is needed, the Inbox and push point to that thread.

03

Schedule a Bot

Set time, timezone, model, and permissions. The routine runs in the container without a connected client, creates its own history, and does not repeat uncertain external effects after failure.

04

Log into a site for the Bot

The Bot stops at login and sends “Needs you”. Open the Linux screen of that thread via web or iPhone, take control, authenticate, and return the session. The Bot observes the result before continuing. Restart the container and check that the browser session persists when the site allows.

05

Switch or recover the machine

Deploy the same image on a new host with the restored volume. Check workspaces, Bots, files, threads, and tasks; secrets that cannot migrate require new authorization.

06 / Delivery path

Prove the heart of the product before scaling.

The first proof combines Elysia backend, Eden contract, Linux GUI, Distill, and linux-use in the same container, with real observation and input in the graphical session. The first usable delivery is a vertical journey: create workspace, run Distill, receive a login request, and take/return the session via mobile. Only then do we expand Git, terminal, routines, and other screens.

1Prove the core

Elysia and Distill in the container; shared Eden client, process isolation, and version contract. Prove Linux GUI without Mac as host.

2Close the first journey

Minimal workspace → Distill edits file → Bot pauses at login → user takes and returns via web and mobile. Use the same backend and services that will be expanded.

3Expand the work

Persistence, files, Git, terminal, history, Bots, routines, and notifications without changing the architecture of the first journey.

4Deliver the clients

Web on macOS, Windows, and Linux and window in the container GUI with the same UI; iOS and Android with their own UI and common services. Prove keyboard, push, and resumption on each target.

5Open the offerings

Self-installation and hosted service with isolation, backup, update, version compatibility, support, and measured cost.

End-to-end proof for the beta

In two isolated accounts: create workspace and Bot, work in Linux GUI and continue on web/desktop/iOS/Android using the same services and Eden connection; a contract change must appear on all clients. Test previous client with updated server and clear message when incompatible. Run Distill and task without connected client, receive push, restore volume in new container, and confirm no user accesses another host nor the agent reads backend secrets. Repeat the journey with network cut, request without response, Docker frozen, full disk, and restart during takeover; compare receipts, files, and states before approving the beta.

07 / Decisions still needing proof

What still needs to be truly discovered.

Security

How to share the host among Bots?

The proposal is one screen and one visual session per Bot inside the user's host. We need to decide the real scope of cookies, profiles, files, and credentials, without suggesting that separate screens isolate secrets. It is also necessary to prove control takeover without dispute between Bot and user.

Remote connection

How does the Linux GUI serve all clients?

The common UI talks to Elysia via HTTP/WebSocket; the linux-use provides local tools to Distill, and an authenticated channel transmits the Linux session screen and input to the person. Prove capture, click, typing, and exclusive control in the container: the current linux-use does not yet implement these actions.

Operation

What size and price are feasible?

4 GB is a hypothesis. Measure GUI, agent, build, and browsers simultaneously, as well as disk, backup, network, and idleness before defining a paid plan.

Distribution

How to keep the two offers equivalent?

Define open license, self-installation, updates, export, and push for those hosting without using our cloud.

Status of this plan

This is a vision and a sequence of proofs, not a statement that the Linux port, desktop GUI, web interface, or server capacity already work. The current macOS app remains the function reference; parity will be confirmed by real journeys.
