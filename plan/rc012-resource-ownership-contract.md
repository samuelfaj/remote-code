# RC-012 resource ownership contract — proposal

## Status and scope

This is a design proposal for RC-012 review, not an implementation or acceptance record. It defines identity, stable resource IDs, parent relationships, and the ownership check every resource route must apply. It does not create placeholder APIs or claim that Bot, thread, file, or scheduled-task functionality exists.

RC-012 remains unaccepted until its original delivery, cross-user read/write proof for every implemented resource route, and failure condition have all been verified. A resource type with no route cannot be counted as proven by this contract.

## Identity and identifiers

- The API derives `userId` only from the validated, persisted server-side session. Request bodies, query strings, route parameters, headers, resource IDs, and parent IDs never select the principal.
- Every persisted resource has an immutable opaque UUID `id`, generated by the backend. IDs identify records; possession of an ID grants no authority.
- Ownership is derived through persisted parent relationships. Denormalized owner fields may support indexing only when database constraints and transactional writes keep them consistent with the authoritative parent; they never replace parent-owner verification.
- The existing `local` login remains a single host identity. Two-user authorization tests may seed two separately persisted sessions as fixtures to exercise backend owner enforcement; this proves route authorization, not account creation, gateway routing, or a two-account login journey.

## Ownership graph

| Resource | Authoritative parent | Required ownership rule |
| --- | --- | --- |
| Workspace | Authenticated user | `workspace.user_id = session.userId`. |
| Bot | Workspace | Its workspace must belong to `session.userId`; a Bot ID cannot authorize itself. |
| Thread | Workspace; optional Bot | Its workspace must belong to `session.userId`. If it names a Bot, that Bot must belong to the same workspace. |
| File | Workspace | Its stable file record must resolve to a workspace owned by `session.userId`. Filesystem path resolution and version/conflict behavior remain in the file feature task; path input is not an owner identity. |
| Workspace scheduled task | Workspace | Its workspace must belong to `session.userId`. This is distinct from a Bot routine. |
| Bot routine | Bot, then Workspace | Its Bot must resolve to a workspace owned by `session.userId`; the routine cannot be moved across owners by changing a supplied Bot/workspace ID. |
| Profile | Authenticated user | Profile key is the session user; callers cannot choose another profile owner. |
| Workspace history | Workspace | Both the workspace and every history row must resolve to the session owner. |

The `workspace_task` / `bot_routine` distinction follows the product backlog, which separately names workspace scheduled tasks and Bot routines. If a future API uses a shared schedule table, it must preserve these typed parent relationships and enforce the matching parent type.

## Route enforcement

- Private reads first authenticate, then query the requested resource through its authoritative parent and `session.userId` in the same database operation. A missing or foreign-owned resource returns the same not-found result (404) to avoid confirming another user's identifier.
- Creates accept a parent ID, validate that parent belongs to the session user, and insert the child in one transaction. Any owner ID supplied by the client is rejected by schema validation or ignored only if the existing API contract explicitly requires compatibility; it is never persisted as authority.
- Updates and deletes scope the mutation by the resource ID and owner chain, atomically. A zero-row mutation returns 404 and leaves all records unchanged. Child references (for example a Bot on a Thread, or a Bot on a Routine) must be checked for same-owner and same-workspace consistency before writing.
- List routes filter by the authenticated user's ownership chain. Nested lists additionally require the supplied parent to be owned; foreign and nonexistent parents both return 404.
- Anonymous access returns 401 before reading or mutating private records. Authorization failure never returns a successful empty collection for a foreign parent.
- The feature that introduces a resource route owns its endpoint schemas and domain behavior. It must import/use a reviewed owner-scoped query pattern rather than duplicate unscoped lookups. Do not add generic empty CRUD layers solely for RC-012.

## Proof required for each resource route

For every implemented read and write route for each resource type:

1. Create owner A and owner B records through the real route or fixture boundary, with independently persisted authenticated sessions.
2. Read A's resource using B's session and attempt update/delete/create-under-A-parent using B's session. Expect 404 and compare authoritative database state before/after to prove no effect.
3. Repeat with a nonexistent ID and confirm the external response does not distinguish it from a foreign-owned ID.
4. Attempt a request with an explicit foreign `userId` or parent substitution; verify the server continues to derive ownership from the session and rejects the cross-owner mutation.
5. Verify A's valid reads/writes and B's independent records still work, so isolation does not become a blanket denial.
6. Verify anonymous GET and mutation paths return 401 and create no durable records.

A resource type without shipped routes is explicitly unverified. Integration tests exercise Elysia plus SQLite and inspect persisted state; user-visible end-to-end proof is added by the task that introduces each usable resource journey. Seeded-session API tests do not substitute for gateway/two-account login proof in RC-011.

## Scope boundaries and sequencing gate

- No Bot execution, thread run lifecycle, file-content API, schedule execution, account provisioning, container routing, gateway, or UI is introduced by this contract.
- RC-002 remains unknown and unaccepted; no provider search, authentication, or retry is authorized by this design.
- RC-011 retains its separate `REVISE` decision and explicit container-routing Start. This contract neither depends on nor satisfies RC-011.
- RC-012's Start (`IDs and identity defined`) has an accepted design basis in RC-004 and an authenticated persisted session in RC-010. The current implementation's workspace IDs are backend-generated UUIDs, and the current local identity is derived from the persisted session. This satisfies the stated Start basis, but the full dependency gate is incomplete: the amended backlog also requires RC-068, which remains `To do`. These facts do not accept RC-012.

### Backlog sequencing amendment — applied locally, pending publication

The present backlog creates a semantic acceptance cycle: RC-012 requires ownership proof for file, Bot, thread, and task/routine routes, while their real feature routes are introduced by RC-021/029, RC-022, RC-038/040, and RC-045, which are directly or transitively gated by RC-012. Accepting RC-012 without those routes would violate its delivery and proof; inventing placeholder CRUD would violate the feature boundaries.

The sequencing amendment is now reflected locally in `plan/tasks.html`, pending exact independent review and publication:

1. Added RC-068, “Prove ownership on existing resource routes,” dependent on accepted RC-004, RC-008, and RC-010. Its scope is the reviewed identity/ownership contract plus proof on existing real workspace/profile/history routes only. It explicitly does not accept RC-012 or claim absent resource categories are proven. Its proof exercises persisted A/B session fixtures through Elysia/SQLite, foreign IDs/parents, anonymous access, valid owner access, and database before/after state.
2. Replaced the final RC-012 dependency with RC-068 on RC-021, RC-028, RC-038, and RC-042. All other dependencies and Start fields are preserved. The backlog's common rule requires per-route ownership proof before acceptance of every feature task that introduces or changes a workspace, Bot, thread, file, workspace-task, or Bot-routine route. RC-060 and RC-063 retain RC-012 as a final security/hosting gate.
3. RC-012 remains open as the final cross-resource audit. Its original Delivery, Executable proof, and Failure if clauses are unchanged. Every real workspace, Bot, thread, file, workspace-task, and Bot-routine endpoint must appear in its route inventory and have verified ownership evidence; missing categories remain unverified.

RC-068 is a valid next candidate after this planning amendment receives exact independent review; its direct prerequisites are accepted and the stated source/fixture preconditions exist. It must still pass its own complete Start, real route proof, Failure if checks, and independent review before acceptance. RC-021 remains ineligible because RC-016, RC-018, and RC-020 are unaccepted. Other foundation work must be evaluated against its own unchanged Starts/dependencies; this amendment does not unlock them by implication.

Even after RC-068 acceptance, RC-012 cannot be accepted until all real routes exist and per-route executable proof covers every required resource without changing RC-012's criteria.
