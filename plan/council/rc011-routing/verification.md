# RC-011 T-001 author cross-examination and fresh verification

## Revised thesis T-002

Retain the local proof implementation but make the interfaces and failure contracts explicit before coding:

- Each tenant has an immutable, server-configured identity and unique audience; each tenant API is configured with its own audience and the gateway public key. An assertion for A must fail at B even if request headers, paths, or query values are changed. The request-supplied target is never consulted.
- Auth mode is explicit and server-configured: standalone mode keeps current cookie auth; managed-tenant mode authenticates only the signed gateway assertion, failing closed for absent, invalid, expired, or wrong-audience assertions. Gateway strips caller-supplied auth, forwarding, tenant, and assertion headers before adding its own assertion. For WebSocket, the gateway validates the browser's cookie/session then injects the internal assertion on the upstream handshake; the tenant rejects any missing assertion with no local-auth fallback.
- The gateway owns opaque sessions and tracks their HTTP/WebSocket use. Logout/expiry revokes the stored session, clears the cookie, rejects subsequent requests using the old cookie, and closes all tracked sockets within a specified bound; the browser shows an explicit signed-out/re-authentication state and never treats an interrupted request as successful.
- Set a finite upstream request deadline, abort upstream work when the deadline or client disconnect occurs, use bounded response/body sizes and connection concurrency, and specify WebSocket close behavior on tenant loss and session revocation. Test refused, stalled, disconnected, and concurrent requests and verify bounded cleanup, not only response time.
- Limit the local network claim to the observable threat boundary: tenant A cannot reach tenant B on the isolated Compose networks; only the gateway joins both; neither tenant API publishes a host port. Separately test Docker-host reachability and report it as host administration access, not tenant isolation. Do not claim resistance to a privileged Docker host.
- Use a unique Compose project and fixture-scoped volumes, with explicit cleanup limited to fixture-owned resources and cleanup checked after normal and interrupted runs. Establish both tenants healthy and gateway-reachable before interpreting a negative A-to-B connectivity test as isolation.
- Emit minimal structured redacted outcomes with correlation ID, dependency/failure category, status class, and elapsed duration. Never log credentials, cookies, assertions, keys, hashes, or request bodies.

## Objections and author responses

All responses are based on design-stage evidence; none constitutes implementation/runtime validation.

- O-R1-001 security-privacy / HIGH: Per-tenant audience ambiguity could allow assertion replay across tenants. **ACCEPT.** T-002 requires immutable unique audience per tenant, fixed tenant-side verifier configuration, and real A-valid/B-rejected tests. Validation: signature, audience, expiry, request-tampering, and real API tests. Residual risk: gateway signing-key compromise remains in the trusted boundary.
- O-R1-002 security-privacy / HIGH: Logout may leave upgraded sockets authorized. **ACCEPT.** T-002 defines server-side revocation plus gateway-tracked socket closure, bounded closure, stale-cookie rejection, and no later event delivery. Validation: real browser WebSocket/logout race E2E and server-side cookie request after logout. Residual risk: process crash cleanup is bounded by connection teardown and needs real fixture tests.
- O-R1-003 security-privacy / MEDIUM: Docker-host workloads may still reach un-published ports. **PARTIAL.** T-002 narrows the claim to tenant-to-tenant network isolation and explicitly distinguishes host administrator access; it adds host reachability measurement and truthful reporting. This is not a claim that Compose protects against a privileged host. RC-011's own direct-internal-port failure condition must still be proven from account/tenant networks and clarified against the actual host boundary in executable evidence.
- O-R1-004 reliability-performance / HIGH: Timeouts may leave upstream resource leaks or fail to bound completion. **ACCEPT.** T-002 defines finite deadline, abort on timeout/client disconnect, body and concurrency limits, and concurrency/stall tests. Validation must inspect upstream completion/resource cleanup, not only response status. Residual risk: exact operational limits require calibration but cannot be unbounded.
- O-R1-005 reliability-performance / HIGH: WebSocket can hang on target loss or survive logout. **ACCEPT.** Addressed by explicit tenant-loss close and session-revocation semantics, tested through gateway under target loss and concurrent socket/logout. Residual risk: network partitions may delay observed close; bound must be measured and documented.
- O-R1-006 api-compatibility / HIGH: Assertion transport to browser WebSocket is unspecified. **ACCEPT.** Browser sends its opaque gateway cookie; gateway validates it and injects an internal assertion on the upstream HTTP/WebSocket handshake. Tenant verification is mandatory. Test in real browser and reject missing/invalid assertion with no fallback.
- O-R1-007 api-compatibility / HIGH: Current local authentication may ambiguously coexist with gateway identity. **ACCEPT.** Explicit server-configured auth mode separates standalone cookie auth from managed assertion-only tenant mode. Test both modes and every invalid assertion class.
- O-R1-008 testability-release / HIGH: Interrupted runs may leave Docker resources or contaminate default Compose. **ACCEPT.** Unique Compose project and fixture-scoped volume; documented scoped teardown; test interrupted and repeated fixture runs and ensure unrelated stack/resources remain.
- O-R1-009 testability-release / HIGH: Negative cross-network result could be false due to unhealthy target. **ACCEPT.** Establish tenant B healthy and gateway-reachable before testing bounded denial from A, and prove no published ports/network memberships.
- O-R1-010 operations-observability / HIGH: Failures lack safe attributable telemetry. **ACCEPT.** Add only minimal structured redacted outcome with request/session correlation ID, dependency category, status class, duration. Verify success and failure paths contain no sensitive values.
- O-R1-011 product-ux / HIGH: Login/session failure and recovery semantics are unclear. **ACCEPT.** Define invalid-credential, expiry/revocation, and temporary gateway/tenant-unavailable UI outcomes; preserve existing user data and mark interrupted operations unconfirmed. Cover browser routes, reload, re-auth, stale cookie, and logout with open WebSocket.
- O-R1-012 product-ux / HIGH: Logout may clear UI without invalidating server session and concurrent socket. **ACCEPT.** Covered by server revocation, stale-cookie rejection, socket close/no later event, reload, and real browser verification.
