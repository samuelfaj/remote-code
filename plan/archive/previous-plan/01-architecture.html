Duas formas de operar

A instalação autogerenciada entrega o container com backend e GUI desktop Linux do RemoteCode, a interface web e um volume persistente no host do usuário. Na hospedagem paga, a mesma imagem do container roda inicialmente em uma VPS por usuário; nós operamos conta, provisionamento, atualizações, backups e monitoramento. O container não é a única fronteira de isolamento entre clientes no piloto. Web e iOS acessam o backend do container via gateway autenticado.

Web ligado ao container

O frontend web desenha a interface inspirada nas referências, solicita listas e detalhes pela API do backend do usuário e acompanha runs, threads e notificações por eventos em tempo real. Comandos como abrir workspace, iniciar Bot, enviar mensagem, editar arquivo ou parar run vão ao container; a resposta do backend determina o estado exibido. O gateway resolve conta→container e impede que o navegador precise conhecer o endereço interno do Docker. Na instalação própria, o frontend usa o mesmo contrato de API apontado ao container local.

GUI desktop no container

A GUI desktop Linux roda dentro do container e usa o mesmo backend, IDs, eventos e volume que o web e o iOS. Alterações feitas nela aparecem nos outros clientes após sincronização; cada interface mantém apenas sua seleção e disposição visual local. A janela desktop não é a API do web nem a fonte de verdade. O porte da GUI macOS baseada em AppKit/SwiftUI para uma GUI Linux equivalente é uma entrega própria e precisa ser validado com arquivos, terminal, browser, Agent App e Bots reais.

Fonte de verdade e sincronização

  • O backend do container é a única autoridade para comandos e resultados; GUI desktop, web e iOS não inventam sucesso.
  • As três interfaces consultam os mesmos IDs de workspace, Bot, thread e run; fechar uma interface não encerra agentes, terminal ou tarefas.
  • Arquivos, banco, histórico, runs, tarefas e preferências sobrevivem à recriação do container no volume.
  • Seleção de workspace/thread, abas e disposição da interface podem ser locais a cada interface; dados e execução são compartilhados.
  • Ao reiniciar o container, restaurar estado durável e informar claramente quais processos interativos terminaram. Scheduler e runs não dependem de nenhuma janela aberta.

Browser e localhost

O browser automatizado roda no container; o web apresenta seus resultados e o preview por endpoints autorizados do backend. Serviços locais expostos por preview usam proxy privado com autenticação por conta e proteção contra acesso arbitrário à rede. A automação de Bots usa perfil Linux próprio; logins do Chrome do Mac não são copiados.

Token Saver e provedores

Provar Claude, Codex e Grok no Linux antes da promessa de paridade. O caminho MLX/Core ML local do Mac não é portável diretamente ao Linux: escolher implementação cloud compatível somente após benchmark/licenciamento. Até lá, indicar capacidade indisponível sem alterar a fórmula nem afirmar economia não medida.

Fronteira de execução

Executar terminal e agentes como usuário Linux sem acesso aos segredos e sockets do plano de controle. O gateway associa cada RPC, stream, upload e preview ao container autorizado e não expõe sua porta diretamente. Testar troca de conta, IDs de workspace adulterados, root e portas de preview adulteradas. Preview fica em origem separada do app web, sem cookies compartilhados; credenciais de provider são entregues apenas ao run autorizado.

Contrato de cliente e eventos

  • Negociar versão da API e capacidades; cliente antigo recebe erro explícito de operação indisponível.
  • Snapshot versionado com cursor e eventos em sequência permitem reconexão sem perder mudanças; se o cursor expirar, refazer snapshot.
  • Cada mutação usa ID estável e recibo de resultado; após timeout, consultar o resultado antes de tentar novamente.
  • Eventos duráveis alimentam interfaces, inbox e push; cliente lento refaz snapshot sem alterar o estado do container.
