# Failure states and operation budgets

## Scope and status

This contract records the existing API/client boundary and RC-004 state ownership rules for RC-017. It does not accept RC-017: the complete three-point proof is still required for all six operation classes. A route not present in this repository is explicitly `not implemented`, not a passing or skipped test. Timeout values below are client-side caps, not a claim that server-side work or external effects stop at that time.

`Unknown` means the caller cannot determine whether an effect occurred. It is not equivalent to failure. A timeout, cancellation, lost connection, or absent response never proves rollback. Reconcile using authoritative durable state or a correlated provider receipt; do not automatically resubmit while the effect is unknown.

## Required failure points and allowed outcomes

The three points are: (1) before acceptance, (2) after a durable effect but before the response reaches the caller, and (3) after the response reaches the caller but before a later observation/recovery step. The third point tests that subsequent state is read from the authority rather than replayed from local assumptions.

## Proof ledger and acceptance gates

- **Implemented client behavior:** `packages/client/src/index.ts` applies a 10-second default client deadline, caller cancellation, and typed `request_outcome_unknown` when an abort occurs. A non-abort network failure is not normalized to that type; this boundary distinction requires further review and tests before acceptance.
- **Existing proof:** `packages/client/src/index.test.ts` exercises read timeout before headers, response-body timeout, stream timeout, and caller cancellation. `apps/api/src/app.test.ts` exercises authentication persistence/logout/expiry and failure-closed behavior for locked or unavailable SQLite.
- **New RC-017 proof:** the shared Eden client → Elysia → SQLite path has an injected response-body timeout after an action commit; the client reports unknown and later history contains exactly one action. A second test first receives a confirmed action receipt, stalls the following history read until its deadline, then confirms the same receipt from authoritative history without repeating the write. A login response-loss test injects failure after session insertion, observes `request_outcome_unknown`, and verifies one SQLite session remains; the test exposes an unresolved orphan-session recovery defect rather than treating it as acceptable. These tests do not prove idempotent retry safety; that remains RC-018.
- **Still required for acceptance:** Three injected points for each of read, local write, command, login, routine, and billing, with an observed allowed state at each point; an explicit total end-to-end deadline for every live boundary (including server execution); cancellation/offline semantics; and receipts/recovery responsibilities. Command, routine, and billing have no executable surfaces in this source tree, so their proof requires those product surfaces and must not be simulated as successful implementations.
- **Failure if:** Any task implementation maps timeout/cancellation to certain failure or success without consulting authoritative state; a live boundary has no total deadline; an uncertain write is replayed without a receipt or provider reconciliation; or a missing route is recorded as passed.
