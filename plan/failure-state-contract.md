# Failure states and operation budgets

## Scope and status

This contract records the existing API/client boundary and RC-004 state ownership rules for RC-017. It does not accept RC-017: the complete three-point proof is still required for all six operation classes. A route not present in this repository is explicitly `not implemented`, not a passing or skipped test. Timeout values below are client-side caps, not a claim that server-side work or external effects stop at that time.

`Unknown` means the caller cannot determine whether an effect occurred. It is not equivalent to failure. A timeout, cancellation, lost connection, or absent response never proves rollback. Reconcile using authoritative durable state or a correlated provider receipt; do not automatically resubmit while the effect is unknown.

## Required failure points and allowed outcomes

The three points are: (1) before acceptance, (2) after a durable effect but before the response reaches the caller, and (3) after the response reaches the caller but before a later observation/recovery step. The third point tests that subsequent state is read from the authority rather than replayed from local assumptions.

## Proof ledger and acceptance gates

- **Implemented client behavior:** `packages/client/src/index.ts` applies a 10-second default client deadline, caller cancellation, and typed `request_outcome_unknown` when an abort occurs. A non-abort network failure is not normalized to that type; this boundary distinction requires further review and tests before acceptance.
- **Existing proof:** `packages/client/src/index.test.ts` exercises read timeout before headers, response-body timeout, stream timeout, and caller cancellation. `apps/api/src/app.test.ts` exercises authentication persistence/logout/expiry and failure-closed behavior for locked or unavailable SQLite.
- **New RC-017 proof:** shared Eden/Elysia/SQLite tests cover a committed action whose response body times out, a later history read recovering a confirmed receipt, an offline read, and API restart after a successful history response followed by a new client reading the same durable action receipt. Login tests cover incorrect credentials before acceptance (401 and no session), a failed session observation after confirmed login followed by successful revalidation, and a lost-cookie timeout after session insertion (unknown to the caller with one orphan session). The orphan-session case remains unresolved for legacy ID-less API calls; the keyed backend recovery proof is recorded below. Those initial tests do not prove idempotent retry safety. RC-018 now adds action-only canonical replay/lookup tests, including a timed-out response, fresh Eden client, API-instance restart, owner scoping, conflicting payload, concurrent repeat requests, and atomic rollback on receipt insertion failure. Other mutations and client/gateway retry policy remain open.
- **Still required for acceptance:** The full three-point table is still required for all six operations, with allowed states observed at every point. Read, local write, and login now have operation-specific shared-client/API integration cases for pre-acceptance or offline, interrupted-response, and recovery outcomes. Browser and installed-iOS auth recovery have local proof; remaining operation-class consumers and end-to-end server deadlines remain unproven. A legacy ID-less login can still leave an orphan session without a retained handle. Command, routine, and billing have no executable surfaces here; their proofs require real product paths and must not be simulated as passing.
- **Failure if:** Any task implementation maps timeout/cancellation to certain failure or success without consulting authoritative state; a live boundary has no total deadline; an uncertain write is replayed without a receipt or provider reconciliation; or a missing route is recorded as passed.

## Implementation order and evidence ownership

The reviewed written contract permits implementation of RC-018, RC-019, RC-020, and RC-027 after their other prerequisites pass. It does not accept RC-017 or promote a phase. Every feature introducing or changing an operation must prove its applicable three failure points through the real product boundary before acceptance, including authoritative effects, total deadlines, cancellation/offline behavior, recovery ownership, and client-visible state. Missing routes and mock-only effects remain unverified.

- RC-018 owns stable mutation identity and receipt recovery, including login/session mutations and gateway waiting/retry behavior. Existing-route implementation alone cannot accept the whole task.
- RC-020 owns full-disk, lock, corruption, restart, integrity, and degraded-client read/write proof.
- RC-009/022/027 own command lifecycle and reconciliation; RC-030/031/032 must additionally prove their Git, PTY, and SSH boundaries.
- RC-045 owns all three failure points for both workspace scheduled tasks and Bot routines, preserving occurrence identity and timezone/DST requirements.
- RC-061 owns provider-backed billing reconciliation, including duplicate and out-of-order webhooks.
- RC-017 remains the aggregate gate for all six operation classes; RC-065 now directly requires its acceptance. No original RC-017 Delivery, Executable proof, or Failure if field is reduced.

RC-002's unknown provider effect and no-retry boundary are unchanged. RC-019 and RC-027 retain their live-execution prerequisites. Phase 01 promotion still requires request, Docker, and storage recovery; early Phase 02 work is not authorized by this amendment.

## Next auth slice: reconcile the effect, then explicitly revoke

The backend and browser/installed-iOS auth recovery portions are implemented and locally tested; full RC-018 acceptance remains open. Read-only reasoning advice `01a0e3b9-93e2-7e43-82ea-98a1d89a317a` recommended preserving random 256-bit session tokens, hash-only persistence and HTTP-only cookies. A lost cookie is not reconstructed, stored as recoverable bearer material, or derived from the password.

- A client retains a login request ID before sending. An auth-local durable receipt records its canonical non-secret result atomically with the session. Repeating that ID never creates a second session or issues another cookie; canonical replay means the receipt, not a secret-bearing response header.
- A valid session or freshly verified host password is required to inspect a receipt. UUID possession is never authentication. Passwords remain transient and are never receipt fingerprints or URL parameters. Password-bearing recovery routes retain the login transport restrictions.
- If the current cookie validates for the original login ID, use that confirmed session. Otherwise the user explicitly revokes/fences the old login through a separately identified, durable mutation. Only authoritative confirmation of that revocation permits a distinct login.
- Missing receipts remain unknown. Revocation must also fence a not-yet-accepted login ID, so a delayed original request cannot create a session afterward. Expiry, logout and targeted revocation never allow an old login ID to mint another session.
- Logout keeps its current all-user-session scope on first acceptance. Its receipt prevents replay from deleting sessions created later. Targeted orphan revocation affects only its original login. Capture WebSocket identities before deleting session rows, commit, then close affected clients.

The first implementation may retain current ID-less login/logout routes only as explicitly legacy/non-recoverable compatibility paths. Those callers, storage client recovery wiring, future mutation families, server/gateway deadlines and retry budgets stay open for full RC-018 acceptance. The new capability must be negotiated before clients rely on it.

Required falsifying proofs come from RC-018's three failure points: lost cookie then API restart and receipt lookup; receipt-confirmed revocation with its own lost response; delayed login arriving after a revocation fence; replay after logout/expiry; old logout replay after a newer login; wrong credentials against known IDs; atomic rollback when receipt storage fails; and actual browser/native cookie-jar behavior. No new Distill action is authorized.

### Local web and installed-iOS action receipt observation

After a stable action ID is saved, the browser gives the POST at most six seconds of client waiting and reserves the remainder of a ten-second window for one read-only receipt lookup. A confirmed receipt clears the pending ID; a missing, unavailable or stalled lookup stops waiting and keeps the ID for an explicit later check. An automatic 401 lookup hides private state, closes the live socket and preserves the pending ID in tab storage. No POST is automatically replayed. Local browser tests cover committed-but-lost response, exact receipt, missing and stalled reads, authorization failure, reload, late response after logout and a short session lifetime. Capability negotiation and ID persistence precede this window; it is not a total click-to-result deadline. The installed iOS app now also makes one locally verified read-only lookup after an uncertain action POST. Multi-attempt delay/jitter budgets, full click-to-result and server/gateway deadlines, other mutation classes, Android and deployed behavior remain open.

## Implemented auth backend boundaries

Auth IDs must use the 36-character hyphenated UUID representation and are normalized to lowercase before lookup, comparison or storage; URN-prefixed representations are rejected before mutation. `POST /api/auth/login` accepts an optional UUID `requestId`; keyed creation commits the session and immutable receipt together. Same-ID replay returns the original non-secret result without another cookie. `GET /api/auth/session` includes `loginRequestId` for keyed sessions so clients can distinguish a matching cookie from an older session. Historical `session_created` is not proof of a currently authenticated client.

`POST /api/auth/receipts/:requestId/lookup` is read-only and accepts a valid same-owner cookie or a password in its body. It returns the immutable receipt plus separately labelled current session status. `POST /api/auth/login/:loginRequestId/revoke` requires current host credentials and a distinct request ID; it revokes only that session or fences the not-yet-accepted login. A replay does not repeat its effect. Keyed logout preserves its original all-user-session scope, but replay under a newer valid session returns only its receipt and does not clear the newer cookie. After a cookie is revoked, use credential-authenticated receipt lookup, not the dead cookie as mutation authority.

These paths preserve random tokens and hash-only storage, sanitize auth validation responses, and protect password-bearing recovery ingress including normalized/trailing-slash paths. Tests cover real HTTP response loss and fresh clients, actual API-process restarts, targeted sockets and atomic rollback. Current browser and installed-iOS auth UI use keyed calls and confirm a matching cookie; legacy ID-less API callers remain non-recoverable after a lost cookie. No auth timeout or absent receipt is treated as rollback.
